# Этот документ по стилизации кода вступает в силу немедленно v1.0.1

# Backend 

## 1. Имена файлов

Имена файлов должны быть логические никаких нижних test_test.go
Всё должно быть так test-test.go

## 2. Функции в файле

В одном файле должна быть ровно одна функция которая выполняет одну операцию

## 3. Файлы должны быть короткими

Никогда нельзя использовать приватные функции в файлах чтобы не раздувать их размер всё должно выноситься в отдельные модули либо хелперы

В файле основной операции не допускаются дополнительные helper/private functions

## 4. Стилизация импортов

Ни в коем случае нельзя использовать gofmt
Так как он ломает стилизацию импортов 

### Импорты должны быть такими
Импорты сортируются по длине строки от самой длинной к самой короткой; при одинаковой длине порядок не важен

```go
import (
	"Analog-WakaTime-Billing-Service/models"
	"Analog-WakaTime-Billing-Service/db"
	"github.com/gin-gonic/gin"
	"net/http"
)
``` 


### Они не должны быть такими

```go
import (
	"Analog-WakaTime-Billing-Service/db"
	"Analog-WakaTime-Billing-Service/models"
	"net/http"
	"github.com/gin-gonic/gin"
)
```


Если код будет отформатирован PR автоматически отклоняется


## 5. Коментарии в коде

Комментарии в коде желательно не использовать они почти ни на что не влияют

Три правила комментариев в коде

### Правила номер один

Комментарии должны объяснять тяжёлую логику но не должно быть простыни текста


### Правила номер два

Комментарии не должны объяснять что делает к примеру
Такой стиль сразу отклоняется и не должен использоваться

```go
// Check if user exists
if user != nil {
    // User exists
}
```

### Правила номер три

Никаких матерных слов в комментариях 
Он должен объяснить тяжёлую логику в внутри кода но не должно объяснять супербанальную штуку 
И комментарии ни в коем случае не должны содержать матерных слов


## 6. Логика должна быть простая и понятная

Если это 5-ти летний ребёнок не поймёт логику тогда это плохое решение проблемы

### Почему так?

Ты можешь ошибиться в своей гениальной логике и потом сам не сможешь её исправить
И это будет ошибка которую будет сложно исправить в будущем

### Никгда не используй чужие идеи

Или решения их кода

### Почему так?

Если ты будешь использовать чужие идеи или решения их кода то ты не научишься решать проблемы самостоятельно
А значит ты не сможешь работать в будущем самостоятельно
А это плохо


### Всегда думай о безопасности

Никогда не используй небезопасные функции и библиотеки
Если ты не уверен в безопасности функции или библиотеки то не используй её
Если ты не знаешь как безопасно использовать функцию или библиотеку то не используй её
Лучше потрать лишнее время на поиск безопасного решения чем потом разбираться с последствиями
Если есть какие-то вопросы по поводу безопасности то обязательно спроси owners или тимлида

# Frontend

## 1. Запрет сборки фронта

Ни в коем случае нельзя собирать фронт (`npm run build`, `npx tsc -b`, `vite build` и т.д.)
Фронт собирает только владелец, агент ограничивается чтением и правкой исходников
Если в сборке будут ошибки владелец сам скинет их в чат

## 2. Просмотре архитектуры Frontend'а

Перед тем как что-либо делать frontend'е ты должен ознакомиться с его архитектурой
Никогда не пытайся изменить структуру frontend'а без разрешения владельца
Иначе твой Pull Request будет автоматически отклонен

Никогда не пиши код без ознакомления с архитектурой frontend'а
Если ты хочешь что-то изменить в архитектуре frontend'а то обязательно спроси владельца


Перед тем как начать писать код ты посмотреть на то как конкретно реализована логика на других модулях


## 3. Не хардкодить текст в компонентах и коде

Для всего текста есть отдельный файл конфигурации и переводов 

### Никогда не используй такие подходы

```tsx
// Никогда не делай так
const buttonText = 'Нажми меня'

// Используй так
const buttonText = textConfig.buttonText
```
